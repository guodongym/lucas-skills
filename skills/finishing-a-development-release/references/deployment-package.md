# Version Deployment Package Reference

仅在 `finishing-a-development-release` 命中部署材料条件或用户明确要求时加载本规范。本文件定义如何在最终验证与打 tag 之前，将上一基线到当前版本之间零散的 PR 过程产物、代码真实变更与数据库 SQL 整理为入库随 tag 固化的运维交付材料。

## 1. 触发深度与基线锚定

### 1.1 触发与内容深度
- **显式指令优先**：用户明确开启则执行；用户明确跳过则立即放行（在最终报告 `Deployment package` 与 `Residual risk` 记录覆盖仓规理由）；历史 tag 补建平台 Release 模式不触发入库生成。
- **“每版必出”仓规**：目标仓库规则明确要求每个版本都须产出部署/升级记录且用户未显式跳过时，**必须触发**，但仍须按第 2 节完整盘点实际变更——存在配置/环境变量、数据库迁移、依赖、基础设施或运维步骤变更时，交付完整部署文档与配套脚本；仅当盘点确认本版本确实无运维操作变更时，才产出简短版本记录（说明无迁移及需更新组件）。
- **一般项目双信号**：无显式指令且无“每版必出”仓规时，须同时命中“项目可部署信号”（部署配置、迁移/SQL 目录、服务配置模板或部署文档声明）与“版本变更信号”（影响部署运行的真实变更或新增/修改 PR 过程产物）；仅命中弱信号且归属不明时，写入前向用户简短确认。纯文档、Skill 集合、纯库或本地 CLI 仓库跳过。

### 1.2 版本基线 `vPrev` 与生产实际起点
- **正式稳定版本**：默认编写基线锚定到**上一个稳定正式 tag**，绝不将中间 RC/测试 tag 当作生产升级基线；区间内存在已发布的测试/RC tag 时，在 `DEPLOY.md` 单列测试环境相对该 RC 的差异或幂等注意事项，且受管迁移兼容性检查仍须将该已发布 RC 纳入支持的其他升级起点分别核对（见 6.2 与 6.3 第 6 条）。
- **允许显式指定实际起点**：用户明确告知生产停在更早版本（如跳过了此前已发但未上线的正式版）并指定起始 tag/SHA 时，按指定起点整理跨版本材料。
- **测试/预发版本（RC）**：默认基线仍指向上一个稳定正式 tag（保证交付包适用于干净测试环境），并附相对前一 RC 的增量差异；用户显式指定基线时遵从用户指定。
- **首次发版（无历史发布 tag）**：基线记为 `initial`，标明“首次全量部署”；**禁止**用 `initial_commit..HEAD` 普通两提交 diff（会遗漏首次提交已有文件），必须直接盘点目标提交的**完整文件树**。
- **基线无法唯一判定**：停止并请用户确认 `vPrev`，不得猜测。

## 2. 原料采集与底账反向核对

1. **底账扫描（强制，路径状态先行 + 敏感配置本地脱敏比对）**：
   - **第一步只盘点路径与变更状态**：增量发版先用 `git diff --name-status vPrev..HEAD`（含重命名检测）与提交记录清单；首次发版先用 `git ls-tree -r --name-only HEAD` 盘点完整文件树。
   - **敏感配置严禁原始全文 diff**：对可能含真实凭据、Token、密码、密钥或私有连接串的配置文件（即使已版本化入库，如 `.env*`、非示例的 `config/`、含密钥段的 `*.yaml`/`*.yml`/`*.toml`/`*.json`/`*.ini`/`secrets*`），**禁止**直接运行原始 `git diff` 或打印全文，防止旧值与新值在生成文档前泄露进**工具输出**或 Agent 上下文；必须先在本地通过脚本/工具比较新旧版本，**只向 Agent 输出键名、变更类型（新增/修改/删除）、结构变化与必要非敏感元数据**。无敏感值的代码、SQL 与纯占位示例模板（如 `.env.example`）再按需读取具体差异。
   - 按上述方式逐类盘点五个运维影响面：
     - 环境变量与配置模板（`.env*`、配置示例、服务配置及字段联动，如禁止对已有环境使用 `--force` 覆写手工配置）；
     - 数据库变更（受管迁移目录含自有迁移链的完整 `A/M/D/R` 清单、零散 `.sql`、ORM 模型/表定义与查询字段）；
     - 构建与运行依赖（包清单、lockfile、基础镜像或系统包）；
     - 服务运行形态与制品渠道（容器、编排、反向代理/端口、启动入口、进程管理、制品/镜像构建方式）；
     - 异步与外部集成（定时任务、消息队列、缓存结构/刷新需求、外部回调与权限）。
2. **过程产物收集（补充）**：检索区间内新增/修改的零散部署文档、过程脚本、零散 SQL，以及当前范围可读的 PR 描述/提交说明。
3. **交叉对账与去重**：
   - 代码有变更但过程产物漏写 → 补齐入部署材料，并在影响清单注明“由代码 diff 补漏”；
   - 过程产物提及但已被后续 PR 撤回/覆盖 → 剔除废弃步骤；
   - 多 PR 对同一配置/依赖/脚本的连续改动 → 合并为面向 `vPrev -> vNext` 的净变更（net delta）并排定顺序。
4. **原过程产物只读保护**：对仓库内原有零散 PR 过程文档、笔记或脚本**绝不自动删除**；明确识别出已过期的一次性临时笔记时，仅在最终报告中列为可选清理建议。

## 3. 目录落地规范与幂等复用

- **优先沿用目标仓库既有规范**：先检查目标仓库的发布文档、规则文件及历史目录；已有既定发布目录或 SQL 归档目录规范时严格沿用。项目已有 SQL 归档目录规范时，在 `DEPLOY.md` 直接引用原相对路径与执行顺序，不重复拷贝一份到兜底 `sql/` 造成双份漂移。
- **兜底默认目录**：目标仓库无既有规范时落到 `deploy/releases/<version>/`（`<version>` 与目标版本/tag 一致）：
  - `DEPLOY.md`（必填）：面向运维的正式版本部署文档；
  - `scripts/`（按需）：仅当本版本确实需要配套可执行脚本时创建（如 `deploy.sh`、`verify.sh`、`rollback.sh`）；无需额外脚本时禁止建空目录或无实质内容的包装脚本；
  - `sql/`（按需）：仅当项目无既有 SQL 归档规范，且属于（1）无受管迁移机制时的存量增量升级 SQL，或（2）受管迁移机制中经确认合法的框架外 DBA/运维手工 SQL 时创建，按执行顺序编号（如 `01_pre_...sql`、`02_ddl_...sql`、`03_post_dml_...sql`）；无数据库变更、纯受管迁移或已有 SQL 归档规范时均不创建。
- **同版本目录幂等保护**：若目标版本目录已存在，先将拟生成内容与现有目录比对——**内容完全一致**时直接复用（记为 `reused`，不打断用户）；若存在实质差异需要覆盖或修改已有内容，暂停并报 `Blocked` 请求用户明确确认。

## 4. `DEPLOY.md` 七章内容契约

面向不了解开发过程上下文的运维与 DBA，固定覆盖以下七节（无变更的节用一句话说明“本版本无变更”）：

1. **版本、基线与适用前提**：目标版本、编写基线 `vPrev`（tag 与 SHA，首次发版记 `initial`）、RC 环境差异、适用环境（测试/生产）、停机或顺序滚动要求；明确写清本文档适用的应用与数据库**起始版本**、运维执行前核对现场实际版本/已执行脚本的具体检查命令，以及跨版本补齐原则（现场实际版本早于文档起点时，须先补齐跳过版本的迁移与配置步骤，严禁无视现场起点直接套用）。
2. **变更影响清单**：
   - 配置与环境变量净变更表（键名、新增/修改/废弃、适用环境、示例格式、获取方式；严禁写入任何**明文密钥**、Token、密码或私有连接串）；
   - 数据库变更概要（清晰区分**仅限空库新装**与**存量环境升级**；列出受管迁移清单与目标结构版本、合法框架外手工 SQL 及 `pre-migration` / `post-migration` 顺序，或既有归档路径/整理后存量增量 SQL 列表、各自前置条件及锁表/不可逆评估）；
   - 依赖、基础镜像、端口、定时任务、队列、缓存及外部集成影响，以及代码 diff 反向检出的补漏项。
3. **部署前置条件与制品获取边界**：备份要求（数据库与敏感配置文件备份、权限与一致性核对）、权限与外部依赖就绪项、停机窗口；若存在必须在打 tag 后才由 CI/流水线生成的不可变制品（如容器镜像 `sha256` 摘要、归档校验和），标签内 `DEPLOY.md` **严禁臆造摘要**，必须写清发布渠道、按 `sha256` 摘要拉取核验的方法，以及发布后最终摘要的权威查询来源（如平台 Release 附件或发布后交付记录）。
4. **分步执行步骤**：按依赖顺序给出命令与脚本调用方式，清晰区分首次新装步骤与存量升级步骤，并标明测试与生产环境差异点（配置来源、备份前置、人工复核点）。
5. **上线验收（Smoke / Health Check）**：健康检查、数据库结构版本核对、核心接口/任务验证命令与预期成功标志。
6. **回滚方案与不可逆边界**：代码与配置回滚步骤、数据库回滚策略；对删表/删列、不可逆洗数或无反向 DDL 的结构升级，必须显式标注“不可直接回滚”并写清应急恢复路径（停写、保留并核对升级后新增数据、从升级前已验备份恢复并切回匹配程序版本）。
7. **变更来源追踪**：提交范围/主要 PR 列表，以及已知风险或遗留限制。

## 5. 配套部署脚本底线与本地校验

- **单套参数化脚本覆盖测试与生产**：环境差异通过命令行参数、环境变量或外部配置文件注入，严禁在脚本中硬编码环境地址、账号或明文密钥。
- **防呆与严格失败**：Shell 脚本默认 `set -euo pipefail`（其他语言采用等价严格失败机制）；入口校验必需参数、环境变量与前置命令，缺失立即非零退出并提示；写操作或高风险动作提供 `--dry-run` 或明确确认门禁。
- **提交前强制本地静态校验**：Shell 脚本至少执行 `bash -n`（本机已有 `shellcheck` 可附加检查，不新增依赖或安装软件）；Python/Node 等脚本执行对应原生语法检查（`python3 -m py_compile`、`node --check`）；支持无副作用 `--help` / `--dry-run` 时可在本地隔离环境验证。发版流程**严禁直连测试或生产主机执行**任何命令。

## 6. 数据库 SQL 前置分类、双轨规则与六条硬阻断

所有只读识别与阻断检查必须在第一次写入任何部署文件之前完成。

### 6.1 前置识别与四类用途分类
1. **按实际机制识别受管迁移**：涵盖 Flyway、Liquibase、Alembic、Prisma、Django Migrations、golang-migrate 等第三方框架，以及项目**自建**的顺序迁移链（具备版本化顺序迁移目录 + 数据库版本历史/校验和/目录摘要核对 + 专用迁移入口命令）。
2. **先按项目实际入口将区间内全部 `.sql` 划入四类之一**：
   - **空库初始化**（如 `dbinit.sql`、全量建表基线）：仅归入“新装/空库初始化”说明，**绝不混入存量升级清单或升级脚本**；
   - **存量增量升级**：纳入本次存量升级清单与执行顺序；
   - **回滚 / 恢复脚本**：仅归入回滚章节，绝不放入正向升级顺序；
   - **测试 / 夹具 / 示例脚本**：明确排除出运维执行清单。

### 6.2 双轨整理规则
- **轨道 1 — 受管迁移机制（含第三方框架与项目自建迁移链）**：
  - **严禁**重写、合并、重命名或删除任何既有或新增迁移文件；
  - **分别核对主基线与部署文档明确支持的其他升级起点的完整受管迁移清单（覆盖 `A/M/D/R` 全部状态，绝不只筛选新增 `A`）**：保留上一稳定版 `vPrev` 作为生产基线，同时对区间内已发布的 RC/测试版本等其他受支持升级起点分别比对到 `HEAD` 的受管迁移差异：
    - **新增迁移（`A`）**：仅当相对全部受支持升级起点均属新增（或未发生冲突改写）时走正常流程——核对版本号顺序、依赖链与目标结构版本，扫描锁表、删列、非空无默认值、长事务回填等高风险语句；
    - **相对任一起点发生修改（`M`）、删除（`D`）或改名（`R`）**：即使该文件相对上一稳定版显示为 `A`（例如首次发布于 `v1.1.0-rc.1`、随后在正式版候选被原地修改），只要相对任一受支持升级起点（含已发布 RC/测试 tag）为 `M`/`D`/`R`，就必须按项目受管迁移机制核验**历史兼容性**（校验和/checksum、版本历史记录、目录摘要或项目明确允许的可重复迁移机制如 Flyway `R__`）；凡无法证明与已运行该起点迁移的环境兼容的，直接命中下方第 6 条硬阻断，不得仅凭上一稳定版视角当作新增或无变化放行；
  - 在 `DEPLOY.md` 列出迁移清单、适用起始结构版本、目标结构版本、前置只读核对及标准迁移入口命令，在脚本中调用项目标准迁移命令；
  - **框架外存量增量 SQL 分流**：对受管迁移目录之外且已判定用于存量升级的 `.sql`，若为常规表结构 DDL（疑似绕过迁移机制），命中下方第 4 条硬阻断；若确认为迁移机制无法承载的合法 DBA/运维手工步骤（如建扩展、账号赋权、非事务在线操作、迁移后分批洗数），保留原迁移不变，有归档规范则引用原路径，无规范时收入本版本 `sql/`，并在 `DEPLOY.md` 明确标注相对标准迁移命令的执行顺序（`pre-migration` / `post-migration`）。
- **轨道 2 — 无受管迁移机制（手工零散 SQL）**：
  - 仅针对**存量增量升级**类 `.sql` 整理排序（空库初始化与回滚分别归入对应章节）；
  - 项目已有 SQL 归档规范时直接列出原路径、来源 PR/提交与执行顺序，不重复拷贝；无规范时按执行依赖（前置检查 → DDL → 存量数据迁移 → 索引/约束/初始化配置）整理进本版本 `sql/` 并标明来源；
  - 为每条存量增量 SQL 明确写出**适用执行前提与重复执行风险**（例如某条 `ALTER` 仅在目标列缺失时执行、**重复执行**会报错，须给出前置核对方法；能安全补幂等保护时尽量幂等），对有依赖关系的步骤标明严格先后，对彼此独立的步骤允许采用不同合法顺序，并提示已在开发环境逐 PR 执行过部分语句时的差异注意。

### 6.3 六条硬阻断条件（只读预检阶段命中即报 `Blocked`，不写文件、不推进 `main`、不打 tag）
1. 多个 PR 修改同一张表/同一字段存在语义冲突或顺序歧义，无法确定面向 `vPrev -> vNext` 的净 SQL；
2. 存在删表、删列、可能截断数据的改列类型、大表锁表风险，或依赖线上存量数据的不可逆洗数 DML，且未见明确人工确认或分步发布方案；
3. 代码 diff 中明显存在实体/表结构/查询字段变更，但版本区间内找不到对应的数据库迁移文件或 SQL（疑似漏提库表变更）；
4. 受管迁移项目中，出现**已判定用于存量升级**、位于受管迁移链之外且疑似绕过该机制的常规表结构 DDL，须人工决定改写为正式迁移文件或明确批准作为框架外步骤（已明确判定仅供空库初始化的脚本不命中本条；用途无法判定走第 5 条）；
5. 版本区间内存在**无法从项目入口**、手册或内容明确判定用途（空库初始化 / 存量升级 / 回滚 / 测试）的 `.sql` 文件，须人工确认用途后再继续；
6. 受管迁移项目中，**已发布**历史迁移文件相对主基线或部署文档明确支持的**其他升级起点**（含区间内已发布的 RC/测试 tag）中的**任一起点**发生修改（`M`）、删除（`D`）或改名（`R`），且无法按项目迁移机制证明与已运行该起点环境的**历史兼容性**（例如存在校验和/checksum、版本历史或目录摘要冲突风险），须人工核实修复或提供经验证的兼容方案后再继续。

# Ezone

使用随包的 `scripts/ezone.py`，Python 3.11+ 标准库即可运行，不依赖 lucas-skills 安装、当前目录或其他 Skill。先按 [命令与环境](references/commands.md) 检查入口、网络和显式仓库标识；涉及 PR／发布再读 [取证与交付](references/pr-release.md)。命令的实际参数以相应 `--help` 为准。

## 工作路径

1. **发现与认证**：先读 `doctor`，核对项目配置路径、HTTPS 主机、企业、repoKey 和凭据来源。首次使用按命令说明配置 `.ezone.json`，由本人在终端 `auth login` 隐藏输入，保存至项目外个人凭据；自动化须同时用可信 `EZONE_HOST` 或显式 `--host` 绑定 `EZONE_TOKEN` 的目标。Agent 不索取或打印令牌，非交互环境不代填登录。Git remote 仅辅助定位，不能当 repoKey；认证探测不证明完整账号身份或所有服务权限。
2. **锚定对象与授权**：记录主机／企业／仓库／PR、不可变 base/head、目标分支及本地 HEAD／未提交排除项。分别核对修复、评论／投票、通知接收人、push、合并、标签／附件／制品的既有授权；API 能力本身不授予权限。
3. **取得完整证据并独立审查**：用当前 PR 事实指定 diff 的源、目标完整 SHA；核对文件清单及完整差异。已有 `code-change-review` 时沿用其判断与输出，端到端任务可用 `review-and-release-pr` 串联；不复制另一套评分规则。没有这些 Skill 也可直接调用 CLI，并使用等价的需求核验、独立代码审查和发布能力。执行者不能把自己的复查当独立审查；缺少独立评审者时只暂停需要独立结论的批准／合并／发布阶段，继续已授权取证、草稿和验证。
4. **核验意见、修复与复审**：分别读取行间评论、总评／投票和提交记录，不把解决标记当修复证据。核对旧意见适用的提交、路径、行号及当前状态；真实协议没有可确认的过时／侧别字段时报告缺口。修复按原需求进行，刷新 head 后对原 base 到最终候选重新独立审查；等价检查可复用，事实刷新本身不要求重跑测试。
5. **交付评审与原生通知**：普通总评使用 `NEUTRAL`，只有明确授权才提交 `APPROVAL`／`REJECTION`。核对同一身份、提交、全文与接收人后写入并回读；只使用 Ezone 原生评审人通知和 @。API 接受通知不代表送达，需接收端可观察证据。超时先核对已有对象，无法确认时保留“结果未知”，不重复发送。
6. **CI、门禁与合并**：刷新 PR、目标分支、规则、门禁、评审和关联构建；无流水线是“未配置”，未知字段／状态是“未核实”，均不能写作 CI 通过。依据项目明确的验收要求判断缺口是否阻塞；不得自行豁免必需门禁。只有独立审查、当前合并树验证、必需检查及相应授权满足后合并。写入超时先回读 PR 和目标分支，不能盲重试。
7. **基于合并提交发布并回读**：确认合并后的实际完整 SHA，再创建代码标签及说明。区分代码标签、产品版本和制品版本；只有 tag 不表示所需附件／制品已发布。按任务要求核对关联、内容校验和、状态及通知，再报告各阶段结果；不代做部署或修改保护规则。

只暂停缺少必要证据／能力／授权的阶段，说明具体缺口。未执行的真实环境验收、模拟响应测试和 Agent 行为演练必须分别报告。

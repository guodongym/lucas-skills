# 版本发布 Skill 运维部署材料整理能力设计

- 日期：2026-11-24
- 状态：已定稿，进入实施计划阶段
- 范围：`skills/finishing-a-development-release/`、`skills/review-and-release-pr/SKILL.md` 及配套自动化测试与评估用例
- 结论：采用“扩展 `finishing-a-development-release` + `references/` 按需加载”的方案，在发版流程的最终验证与打 tag 之前增加条件式“版本部署材料整理”阶段，将上一基线到当前版本之间零散的 PR 过程产物、代码真实 diff 与数据库增量变更整理为入库随 tag 固化的运维部署文档与配套脚本；同时对 `review-and-release-pr` 做最小 handoff 衔接，并将已落地的 `ezone` 随包 CLI 按其真实一次写入模型对齐为可用平台 Release 能力。

## 1. 意图与背景（Intent & Why）

在当前的日常开发模式中，业务项目在开发环境可以基于每个 PR 产生的零散过程产物（临时部署说明、环境变量片段、手写 SQL、脚本补丁）由 Agent 直接部署。但到了测试环境与生产环境，通常无法由 Agent 临场操作，必须交由运维（以及 DBA）依据正式、完整、可复核的材料执行部署。

现有版本发布编排 Skill `finishing-a-development-release` 只覆盖代码集成、`CHANGELOG` 同步、提交历史整理、验证、推送 `main`/tag、创建平台 Release 与安全清理 worktree，不产出面向运维的版本部署交付物。当一个正式版本跨越多个 PR 时，如果只靠人工回忆或简单拼贴各个 PR 的零散笔记，极易出现：

- 代码改了环境变量、配置模板、定时任务或表结构，但过程文档遗漏；
- 多个 PR 对同一配置、同一脚本或同一张表反复修改，存在冲突或执行顺序错误；
- 缺少上线验收标准（Smoke Check）、生产实际起点核对方法与回滚边界（特别是不可逆库表变更警示）；
- 空库初始化 SQL（如 `dbinit.sql`）、存量升级 SQL、回滚脚本及测试脚本混在一起，或零散手写 SQL 与受管迁移机制（含第三方框架与项目自有迁移链）混用不当导致环境校验失败。

本次改造的核心，是在切版本发版时，把**两个版本之间零散的过程产物和代码真实变更做一次正式整理**，产出直接可交付给测试/生产运维的版本部署材料，并随 tag 固化在代码仓库中。

## 2. 目标、非目标与反目标

### 2.1 目标（Goals）

1. **按信号自动触发 + 仓规兜底 + 显式开关**：用户明确要求产出或跳过部署材料时严格遵从；目标仓库规则明确要求每版产出部署记录时按仓规触发；其余场景基于目标仓库可部署信号与版本区间变更信号自动决定是否触发，不拖慢工具库、文档库等无需运维部署的常规发版快速路径。
2. **代码真实变更底账反向核对**：增量发版以 `vPrev..vNext` 的真实代码、配置、依赖、基础设施与数据库变更 diff 为底账，首次发版直接盘点目标提交的完整文件树；交叉核对各 PR 散落的过程产物，补齐漏项、剔除已被后续提交撤回的过时说明、合并去重并理顺执行顺序。
3. **入库随 tag 固化与制品边界清晰**：版本部署材料在最终验证与打 tag **之前**提交进待发布分支/`main`，与目标版本 tag 绑定为同一代码树，支持 Code Review 与跨平台追溯；对必须在打 tag 后才由 CI/流水线生成的不可变制品（如容器镜像 `sha256` 摘要），在标签内文档写清制品获取渠道、核验方式及发布后最终摘要的权威来源。
4. **规范目录优先 + 幂等复用 + 无空目录**：优先沿用目标仓库已有的部署/发布目录与 SQL 归档规范（已有归档路径时直接引用原路径和顺序，不重复拷贝造成两份漂移）；无规范时兜底落到 `deploy/releases/<version>/`，仅创建实际有产物的子目录；同版本目录续跑时内容一致直接复用。
5. **运维就绪交付物**：版本部署文档明确适用的应用与数据库起始版本、现场核对方法及跨版本补齐原则，覆盖变更影响清单、配置/密钥占位（无明文值）、前置条件、分步执行、上线验收与回滚边界；配套一套参数化部署/校验脚本覆盖测试与生产，提交前完成本地静态与防呆校验。
6. **数据库 SQL 先分类再双轨整理**：先按项目实际入口区分空库初始化、存量升级、回滚与测试用途，避免把新装脚本混入存量升级；按实际机制识别受管迁移（涵盖第三方框架及项目自建顺序迁移链），绝不重写或合并受管迁移文件；对框架外零散 SQL 区分“疑似绕过迁移链的裸 DDL（硬阻断）”与“合法 DBA/运维手工 SQL（可共存并标明迁移前后顺序）”；无迁移机制时按执行依赖整理存量增量 SQL，遇高风险、冲突或用途不明立即阻断并人工确认。
7. **只读保留原有过程产物与主工作区安全**：默认只读取汇总仓库中既有 PR 过程产物，不自动删除；阻断门禁前不污染本地 `main` 提交指针与主工作区（含用户原有未提交改动）。
8. **保护分支精确锁 SHA 与平台对齐**：`review-and-release-pr` 保持薄编排，先合入已 `PASS` 的功能 PR，再以独立发布 PR 承载跨版本部署材料，对任意路径下新增/修改的可执行部署内容执行独立审查门禁，合入后锁定平台返回的**该发布 PR 实际合并 SHA** 打 tag；`finishing-a-development-release` 将仓库已落地的 `ezone` 随包 CLI 按其真实一次写入模型对齐为可用平台 Release 能力，并统一 `Portable Release` 定义。

### 2.2 非目标（Non-Goals）

- 不实现通用 CI/CD 构建流水线、制品构建发布系统，也不自动连接测试或生产主机执行部署。
- 不强绑单一部署技术栈（Docker/Compose/K8s/systemd/裸机均按目标项目现状适配）。
- 不默认将部署材料打包上传为平台 Release 附件（已选定入库随 tag 固化；若未来需要附件上传作为单独增强）。
- 首版不编写跨技术栈的通用自动采集脚本（沿用仓库一贯策略，先通过规则与真实版本回放验证，确认高频机械步骤后再评估抽脚本）。
- 不改变既有 `Local State Gate`、唯一恢复包策略，以及 GitHub/Gitee 的既有发布安全契约。

### 2.3 反目标（Anti-Goals）

以下情况即使命令全部执行成功也视为设计失败：

- 将空库初始化 SQL（如 `dbinit.sql`）、回滚脚本或测试/夹具 SQL 混入存量环境升级清单或升级脚本。
- 合并、修改或删除受管数据库迁移机制（含 Flyway/Liquibase/Alembic/Prisma/golang-migrate 及项目自有版本迁移链）的迁移文件，导致已跑过迁移的环境版本链、校验和或目录摘要损坏。
- 首次发版使用 `initial_commit..HEAD` 的普通两提交 diff，导致漏盘首次提交里已经存在的文件。
- 在部署文档、脚本或报告中写入、打印真实密钥、Token、密码或私有环境连接串。
- 只凭 PR 零散笔记拼接文档，遗漏真实代码 diff 中的配置、环境变量、表结构、端口或后台任务变更；或在打 tag 前的文档中臆造打 tag 后才能生成的不可变镜像摘要。
- 对无需运维部署的纯文档、Skill 或本地工具仓库（如 `lucas-skills` 自身）在常规发版时强行生成 `deploy/releases/<version>/`。
- 静默猜测合并存在语义冲突、疑似绕过迁移机制、用途不明，或具有不可逆风险（删表/删列、大表锁表、存量洗数 DML）的 SQL，而不停下来让人工确认。
- 本地 `main` 在部署或 SQL 门禁阻断退出时，已前移提交指针或在主工作区残留半成品文件/改动了用户原有未提交内容。
- 先打 tag 再补提交部署材料，或生成部署材料后复用旧树的测试结果而不覆盖最终提交树。
- 在日常单 PR 合并（不切版本）时误触发跨版本部署材料整理，或把测试/生产拆成两份独立易漂移的部署脚本。
- 向已通过独立审查的功能 PR 直接追加跨版本部署材料导致 `PASS` 失效；由同一上下文自审并自动合并自己新生成的可执行部署内容（无论位于兜底目录还是项目自定义目录）；或在受保护分支合入后盲取“远端最新 `main`”而非该发布 PR 的实际合并 SHA 打 tag。
- 在 Ezone 上沿用 GitHub 两步模型先 `git push tag` 再 `ez release create` 导致接口冲突，在未实测验证前盲目用 `ez release edit` 修改历史 tag，或把“平台有能力但用户未授权平台 Release”误报成“平台无可用 Release 能力”。

## 3. 约束（Constraints）

- **仓库 Skill 架构与测试约束**：
  - `skills/finishing-a-development-release/SKILL.md` 必须保持薄入口（沿用快速路径优先原则），重规则通过同目录 `references/` 按条件渐进加载。
  - `skills/review-and-release-pr/` 受 `tests/test_review_and_release_pr_skill.py` 约束：目录顶层仅允许 `SKILL.md`、`agents/`、`evals/`（不得新增 `references/`），frontmatter 必须保留既有正负向路由关键词。
  - 遵循仓库 `AGENTS.md` 与 `skill-creator`/`writing-skills` 校验要求：`quick_validate.py`、仓库全量 `unittest` 与 `git diff --check` 必须通过。
- **既有契约兼容**：
  - 保留 `finishing-a-development-release` 的四级发布结果（`Full Release` / `Portable Release` / `Partial Release` / `Blocked`）、按动作独立核对授权、以及 `verification-before-completion` 最终树身份等价规则；同步清晰界定 `Portable Release` 的两种合法原因，并针对保护分支发布 PR 实际合并 SHA 与 Ezone 一次创建 tag+Release 补充等价回读判据。
  - `finishing-a-development-release` 不复制 `neat-freak`、`git-history-rewrite`、`finishing-a-development-branch`、`verification-before-completion` 或 `ezone` 的内部操作步骤，只声明调用条件、消费结果与边界。
- **密钥与安全底线**：
  - 严禁读取并输出明文密钥值；配置文件对比沿用“只比较路径、key 名、元数据与等价性”规则。
  - 发版流程严禁直连测试/生产环境执行任何部署或数据库变更操作。

## 4. 方案比选（Approaches）

在确定架构前先排除了两个弱方案：
1. **将全部部署规范、模板与 SQL 规则直接塞入 `finishing-a-development-release/SKILL.md` 正文**：会显著膨胀入口上下文，违背原 Skill“轻量快速路径”定位，拖慢不涉及运维部署的常规发版。
2. **首版预写跨技术栈的通用采集与生成脚本**：不同项目的目录结构、迁移机制、配置格式与部署方式差异很大，预先抽脚本容易脆弱且难以维护，违背本仓库“先用规则和真实版本回放验证，确认高频重复步骤再抽脚本”的一贯策略。

保留并评估了以下两种可行方案：

| 维度 | 方案 1：扩展 `finishing-a-development-release` + `references/` 按需加载（**已选定**） | 方案 2：新增独立子 Skill（如 `release-deployment-prep`）+ 条件编排 |
| --- | --- | --- |
| 结构形态 | `finishing-a-development-release/SKILL.md` 保持薄编排入口，新增 `references/deployment-package.md` 按条件加载（对齐本仓库 `code-change-review` 渐进加载模式）；`review-and-release-pr` 最小透传。 | 新增独立 Skill 专责部署材料整理，`finishing-a-development-release` 在 `Skill Composition` 中以条件式 `REQUIRED SUB-SKILL` 调用它；`review-and-release-pr` 最小透传。 |
| 优点 | 单一发版入口，改动面小；无需通过 `agent-manager` 维护和激活新 Skill，不增加全局触发路由冲突；无部署信号时几乎零额外上下文负担。 | 职责完全解耦；既可随发版自动触发，也可在不合 `main`、不打 tag 的情况下独立调用（例如提测阶段单独出包）。 |
| 代价 | 若需要完全脱离发版流程单独整理部署包，需通过同一发版 Skill 的口令限定范围，略不如独立 Skill 直观。 | 多一个全局 Skill 需同步激活、维护触发边界与独立 eval，并需维护两个 Skill 间的基线/阻断/待提交树交接契约。 |

**选定结论与理由**：用户选定 **方案 1**。本需求的典型场景是围绕切版本（包括测试/RC 版本或正式版本）整理两个版本间的运维交付材料；方案 1 保持最简洁的 Skill 拓扑，避免过早增殖 Skill 与触发路由表面，同时通过 `references/` 渐进加载保证非部署类发版的轻量体验。未来若高频出现“完全不走发版流程、单独生成部署包”的诉求，可将 `references/deployment-package.md` 抽离为独立子 Skill，演进成本低。

## 5. 详细设计

### 5.1 触发与基线判定

#### 5.1.1 触发决策顺序（按信号自动判断 + 仓规兜底 + 显式开关）

1. **显式指令优先**：
   - 用户明确要求生成部署材料（如“顺便出部署文档和脚本”“带运维部署包发版”）→ 强制开启。
   - 用户明确跳过（如“只打 tag 不出部署文档”“跳过部署材料”）→ 依据 `AGENTS.md`（用户当前明确要求优先于项目约定）**立即放行跳过**，不因目标仓库规则额外做二次打断确认；若该跳过覆盖了目标仓库明确声明的发布文档规则，必须在最终报告的 `Deployment package: skipped (user override of repo rule)` 与 `Residual risk` 中显式记录覆盖理由。
   - **历史 tag 补建平台 Release 模式**（[Agent 默认决定]）：由于该模式严禁修改或移动历史 tag 指向的提交树，**不触发**入库部署材料生成。
2. **目标仓库硬性发布文档规则单独触发**：
   - 若用户未显式跳过，且目标仓库规则或发布手册明确要求**每个版本**都须提供部署/升级记录，则**必须触发部署材料整理**（不会因缺少变更信号而跳过）。触发后仍须按 5.3 完整盘点本版本实际变更：只要存在配置/环境变量、数据库迁移、依赖、基础设施或运维步骤变更，就照常交付完整部署文档与配套脚本；仅当盘点确认本版本确实无运维操作变更时，才产出简短版本记录（例如说明无新迁移及需更新的组件）。
3. **一般项目的双信号自动检测**（无显式指令且无“每版必出”仓规时，必须同时满足“项目可部署信号”与“版本变更信号”才触发）：
   - **项目可部署信号**（满足任一项）：
     - 仓库规则/发布文档声明存在运维部署流程；
     - 存在服务运行或部署配置（如 `Dockerfile`、`docker-compose*.yml`、K8s/Helm 清单、systemd/supervisor 配置、Nginx/网关配置、已有 `deploy/` 或历史版本部署目录）；
     - 存在数据库迁移或 SQL 目录（含第三方迁移目录、项目自有顺序迁移目录如 `schema_migrations/` 或 `db/`、`sql/`、`docs/db-schema/`）；
     - 存在服务运行时配置模板（如 `.env.example`、`.env.template`、`application*.yml`、`config/*.example.*`）。
     - 纯文档、Skill 集合、纯库或仅本地运行的 CLI 仓库（无上述服务部署/数据库/发布规范信号）不自动命中。
   - **版本变更信号**（在 `vPrev..vNext` 区间内满足任一项）：
     - 存在影响部署或运行的真实代码/配置变更（环境变量、配置模板、数据库迁移/SQL、构建/运行时依赖、容器/启动脚本、端口/网关、定时任务/队列/缓存结构/外部集成）；
     - 存在本版本周期内新增或修改的 PR 零散过程产物（过程部署文档、增量 SQL、运维脚本）。
   - **信号模糊兜底**：若仓库仅命中弱信号且无法判断是否面向运维部署（例如仅有演示用 `Dockerfile`），在写入任何部署文件前向用户做一次简短确认，不静默新建目录。

#### 5.1.2 版本基线 `vPrev` 锚定与生产实际起点规则

发版整理的是面向升级起点的版本交付，既要选准默认编写基线，也要允许应对生产跳过已发正式版及首次全量部署的边界：

- **正式稳定版本（如 `v1.2.0`）**：
  - 默认编写基线锚定到**上一个稳定正式 tag**（如 `v1.1.0`），**绝不**将中间的测试/预发 tag（如 `v1.2.0-rc.1`）作为生产升级基线；
  - **允许显式指定实际起点**：当用户明确告知生产实际仍停在更早版本（例如跳过了一个或多个已发布但未部署的正式版）并指定起始 tag/SHA 时，按显式指定的起点整理跨版本材料；
  - 若区间内存在已发布的测试/RC tag，在 `DEPLOY.md` 中单列说明：生产按文档起点升级；若测试环境已在某 RC 版本，说明相对该 RC 的增量差异或幂等注意事项。
- **测试/预发版本（如 `v1.2.0-rc.2`）**：默认基线仍指向上一个稳定正式 tag（保证交付包可用于干净测试环境部署），同时在文档中标注相对前一个 RC（如 `v1.2.0-rc.1`）的增量变化；用户显式指定基线时按用户指定的 tag/SHA 执行。
- **首次发版（仓库尚无历史发布 tag）**：
  - 基线记为 `initial`，文档标明为“首次全量部署”；
  - **取数方式禁止使用 `initial_commit..HEAD` 普通 diff**（会漏掉首个提交里已经存在的文件）；必须直接**盘点目标提交的完整文件树**（完整部署配置、环境变量模板、空库初始化 SQL 或完整迁移链、启动入口与验收命令）。
- **基线无法唯一判定**（如非规范 tag 命名或分叉历史导致多个候选基线）：停止并请用户确认 `vPrev`，不猜测。
- **文档必须写明现场核对前提**：因为仅凭 Git tag 顺序无法证明生产环境已经实际部署过上一个正式版，`DEPLOY.md` 必须明确适用的应用与数据库起始版本及执行前核对方法（见 5.3.3）。

### 5.2 编排顺序与三条执行路径

`finishing-a-development-release` 保持快速路径零回归，并针对“本地可合入 `main` + 部署材料”和“受保护分支（PR 模式）+ 部署材料”明确安全顺序：

#### 路径 A：未命中部署材料的常规快速路径（保持原顺序不变，[Agent 默认决定]）
1. 锚定现场、授权、本地状态初始快照，确认部署材料不触发（`skipped`）。
2. 同步 `CHANGELOG` 与直接相关文档（命中治理升级信号时执行 `neat-freak`）。
3. 按需执行 `git-history-rewrite` 预检，集成到 `main`（暂缓 cleanup）。
4. 本地状态对账 + 一次最终验证（`verification-before-completion`，可按既有 tree identity 条件复用）。
5. 推送 `main`、打 tag / 平台 Release 并回读（见 5.4）。
6. 通过六项 `Cleanup Gate` 后清理。

#### 路径 B：命中部署材料且本地可直接合入 `main`（保护本地 `main` 提交与主工作区）
为保证 `vPrev..vNext` 覆盖完整代码增量，同时在命中阻断时确保本地 `main` 的**提交指针与主工作区状态（含用户原有无关未提交改动）均保持原样**：
1. **锚定现场与只读预检（严格先于任何文件写入）**：
   - 记录本地 `main` 当前提交 SHA 与工作区状态基线（区分用户原有无关未提交改动，严禁覆盖、stash 或清理）；
   - 锚定授权、本地状态初始快照、部署材料触发条件与基线 `vPrev` / 目标版本 `vNext`。
2. **准备完整代码候选并执行全部阻断级只读检查**：
   - 若从任务分支发版：先在任务分支（或基于最新 `main` + 任务分支合集的独立临时准备分支/worktree）同步最新 `main` 并按需执行 `git-history-rewrite`，确保候选树已完整包含 `vPrev` 以来全部待发布代码；
   - 若起点就在本地 `main`（无独立任务分支，汇集此前已合入 `main` 的多个 PR）且需要写入发布材料：**一律先在独立临时 worktree / 准备分支上**开展准备，不得直接向主工作区写入文件；
   - 在任何文件写入之前，先完成全部只读检查（代码 diff / 完整文件树盘点、SQL 四类用途分类、五条 SQL 硬阻断检查、既有同版本目录比对、关键部署事实核查）；命中任一硬阻断（SQL 冲突/高风险/疑似绕过迁移链/疑似漏提库表脚本/SQL 用途不明、已有同版本目录内容冲突且未授权覆盖、关键部署事实或基线缺失）→ 立即停在本地并报 `Blocked`，**本地 `main` 提交指针与主工作区均与流程开始前完全一致（用户原有改动原样保留），不残留半成品文件、不 push、不打 tag、不进 cleanup**。
3. **发布内容收口与本地提交**：
   - 全部只读阻断门禁通过后，在隔离准备分支/worktree 中同步 `CHANGELOG` 与直接相关文档（命中治理信号时执行 `neat-freak`），读取 `references/deployment-package.md` 生成/复用部署材料并完成全部本地静态与防呆校验；若静态校验或生成过程出现阻断，同样停在隔离准备区并报 `Blocked`，主工作区与本地 `main` 保持原貌；
   - 全部生成与校验通过并在隔离准备分支完成发布收口提交后，再将本地 `main` 集成（如 fast-forward）到该最终树（暂缓 cleanup）。
4. **本地状态对账与一次最终验证**：在最终待发布 `main` 树上完成所需本地状态对账，并通过 `verification-before-completion` 取得覆盖该精确 Git tree object 的 fresh 证据（项目测试/构建 + 部署脚本本地静态校验证据）。
5. **推送、打 tag、创建平台 Release 与回读**（见 5.4）。
6. **Cleanup Gate 与安全清理**（见 5.6；隔离准备 worktree/分支一律沿用现有六项 Cleanup Gate，仅在发布成功且获授权后清理；任何 `Blocked` 或 `Partial Release` 均保留准备区与重试现场，不做例外删除）。

#### 路径 C：受保护分支 / `review-and-release-pr` 链路（独立发布 PR + 严格审查门禁 + 锁定实际合并 SHA）
1. **先合入已审查通过的功能 PR 并锁定合并 SHA**：若从 `review-and-release-pr` 审完功能 PR 进入切版本发版，绝不向原功能 PR 追加跨版本 `CHANGELOG` 或部署材料；先按已有授权合并该 `PASS` 功能 PR 到 `main`，并保存平台返回的**功能 PR 实际合并 SHA**。
2. **创建独立发布准备分支 / PR**：基于该确切 `main` 合并基线切出独立发布分支（如 `release/<version>`），在其上完成只读预检、`CHANGELOG`、相关文档与部署材料的整理、本地静态校验并提交，按授权推送并创建独立发布 PR（需先核对创建 PR 的授权）。
3. **可执行部署内容的严格审查门禁（按文件用途判定，不限目录名）**：
   - 只要该发布 PR 新增或修改了任意路径下的**可执行部署内容**——包括 Shell/Python/Node 等部署与校验脚本、数据库升级/回滚/手工 SQL、容器/编排/网关/systemd 等基础设施执行配置（无论落在兜底目录 `deploy/releases/<version>/`，还是沿用项目自定义目录如 `ops/`、`deploy/`、`db/`）——禁止由生成它们的同一上下文自审后自动合并；必须经独立评审者/独立上下文审查 `PASS` 且满足目标仓库保护分支审批/CI 门禁，或由人工审批合入 `main`；
   - 若本轮环境无可用独立复审或发布 PR 需等待人工审批合入，流程停在 **`Blocked`（原因明确标注 `release PR awaiting review/merge`，附 PR URL）**，保留分支、worktree 与现场，不打 tag、不创建平台 Release、不进 cleanup；待发布 PR 合入 `main` 后再续跑后续发布阶段。
4. **合入后锁定实际合并 SHA 与并发前移校验**：
   - 发布 PR 合入后，**保存平台返回的该发布 PR 实际合并 SHA**（绝不默认取“远端最新 `main`”），以其树身份对照已审查和已验证的候选树：
     - **合并树与已验证树等价**：以该精确实际合并 SHA 作为唯一目标提交执行 Step 5（打 tag / 平台 Release 与回读）及 Step 6（Cleanup Gate）；
     - **等待审合期间 `main` 并入其他改动导致合并树实质变化**：不得沿用旧验证或旧审查结论；必须重新核对受影响的部署材料、重新独立审查并重新验证该合并候选树后，才能继续合入或打 tag；
     - **发布 PR 合入后 `main` 又出现与本次发布无关的后续提交**：默认仍严格锁定已验证的该发布 PR 实际合并 SHA（不静默把 tag 打到未经验证的更新 `main` 提交上）；若需要把后续提交一并纳入本版本，则停止并请用户确认重新锚定发版范围。

### 5.3 部署材料整理细则（`references/deployment-package.md` 契约）

该文件仅在命中部署材料条件时由 Agent 按需加载，规范以下五个部分：

#### 5.3.1 原料采集与底账反向核对
- **底账采集（强制）**：
  - **增量发版**：扫描 `vPrev..HEAD` 完整 `git diff` 与提交记录；
  - **首次全量发版**：直接盘点目标提交的完整文件树（如 `git ls-tree -r` 及关键部署/配置/数据库文件），不用 `initial_commit..HEAD` diff；
  - 逐类盘点五个运维影响面：
    1. 环境变量与配置模板（`.env*`、配置示例、服务配置文件及配置段联动关系）；
    2. 数据库变更（受管迁移目录含自有迁移链、零散 `.sql`、ORM 模型/表定义与相关查询）；
    3. 构建与运行依赖（包清单、lockfile、基础镜像或系统依赖）；
    4. 服务运行形态（容器、编排、反向代理/端口、启动命令、进程管理、制品/镜像构建渠道）；
    5. 异步与外部集成（定时任务、消息队列、缓存结构/刷新需求、外部回调/权限）。
- **过程产物采集（补充）**：检索区间内新增/修改的零散部署文档、过程脚本、零散 SQL，以及当前范围可读的 PR 描述/提交说明。
- **交叉对账**：
  - 代码有变更但过程产物未记录 → 补齐入部署材料，并在变更影响清单中标明“由代码 diff 补漏”；
  - 过程产物记录了某变更但已被后续 PR 撤回或替代 → 剔除过时操作，避免运维执行废弃步骤；
  - 多个 PR 对同一配置/依赖/脚本的连续改动 → 合并为面向 `vPrev -> vNext` 的净变更（net delta）并确定唯一执行顺序；对明确不可暴力覆盖的配置更新（如不能用 `--force` 覆盖已有手工配置），在文档中显式提示。
- **原过程产物处理**：只读汇总，**绝不自动删除**仓库中原有零散 PR 文档或脚本；如明确识别出已过期的纯一次性临时笔记，仅在最终报告中列为可选清理建议。

#### 5.3.2 目录落地规范（方案 A）
- **优先沿用项目既有规范**：先检查目标仓库的发布文档、规则文件及历史目录结构；已有既定位置、命名风格或 SQL 归档目录规范时严格沿用（已有 SQL 归档路径时在部署文档中直接列出原路径与执行顺序，不重复拷贝一份到兜底 `sql/` 造成双份漂移）。
- **兜底默认目录**：目标仓库无既有规范时，落到 `deploy/releases/<version>/`（`<version>` 与目标发布版本/tag 一致）：
  - `DEPLOY.md`（必填）：本版本面向运维的正式部署文档。
  - `scripts/`（按需）：本版本配套参数化脚本（如 `deploy.sh`、`verify.sh`、`rollback.sh` 或分步脚本）；若本版本无需额外可执行脚本（例如仅标准构建重启加配置变更且已有成熟统一脚本），不强行创建空目录或无实质内容的包装脚本。
  - `sql/`（按需）：仅在项目无既有 SQL 归档规范，且满足以下两种情况之一时创建——（1）项目无受管迁移机制且本版本存在零散手写存量升级 SQL；（2）项目有受管迁移机制，且存在经确认属于迁移机制无法承载的合法 DBA/运维手工 SQL（见 5.3.5）。按执行顺序编号（如 `01_pre_...sql`、`02_ddl_...sql`、`03_post_dml_...sql`，以及可逆时的回滚脚本）。本版本无数据库变更、仅包含纯受管迁移、或项目已有既有 SQL 归档规范时，均不创建该目录。
- **已存在同版本目录幂等保护**（[Agent 默认决定]）：若目标版本目录在准备前已存在（例如此前发版中断后续跑），先将拟生成内容与现有目录比对；**内容完全一致时直接复用（no-op，不打断用户）**；仅当实际需要覆盖或修改已有内容时才暂停请用户确认。

#### 5.3.3 `DEPLOY.md` 内容契约
面向不了解本次开发上下文的运维工程师（及 DBA），固定包含以下七个章节（无相关变更的节可一句话写明“本版本无变更”，避免漏检）：

1. **版本、基线与适用前提**：
   - 目标版本、编写基线 `vPrev`（tag 与 SHA，首次发版标为 `initial` 全量部署）、中间 RC/测试基线差异说明、适用环境（测试/生产）、是否需停机或按序滚动；
   - **生产实际起点声明与现场核对方法**：明确写出本文档适用的**应用起始版本**与**数据库结构起始版本**（以及运维执行前核对当前环境实际应用版本、DB schema 版本或已执行脚本清单的具体检查命令/步骤）；
   - **跨版本处理原则**：写明若现场实际版本早于本文档起点（例如生产跳过了此前已发但未上线的正式版），运维须先按跳过的中间版本补齐跨版迁移与配置步骤（或以实际现场版本为起点重新整理），严禁无视现场起点直接套用本文档步骤。
2. **变更影响清单**：
   - 配置与环境变量净变更表（配置项/键名、变更类型新增/修改/废弃、适用环境、示例格式、获取方式；严禁填真实密钥）；
   - 数据库变更概要（清晰区分**仅限空库新装**与**存量环境升级**；列出受管迁移清单与目标结构版本、合法框架外手工 SQL 及迁移前后顺序，或既有归档路径/整理后存量升级 SQL 列表；注明锁表/时长/不可逆评估）；
   - 运行依赖、基础镜像、端口、定时任务、队列、缓存及外部集成影响；
   - 由代码 diff 反向检出的补漏项说明。
3. **部署前置条件与制品获取边界**：
   - 数据与配置备份要求（尤其生产库与敏感配置文件备份、权限保护及一致性核对）、所需权限、外部依赖就绪项、停机窗口要求；
   - **标签前/标签后制品获取边界**：若本版本涉及必须在打 tag 后由 CI/流水线生成的不可变制品（如容器镜像 `sha256` 摘要、签名归档校验和），标签内 `DEPLOY.md` 严禁臆造或遗留无说明占位，必须写明制品发布仓库/渠道、不可变摘要的拉取核对方式，以及发布后最终摘要的权威查询来源（如平台 Release 附件或发布后交付记录文档）。
4. **分步执行步骤**：按依赖顺序给出命令与对应脚本调用方式，清晰区分首次新装步骤与存量升级步骤，并明确标出测试环境与生产环境的差异点（如配置文件来源、备份前置、人工复核节点）。
5. **上线验收（Smoke / Health Check）**：部署完成后可执行的健康检查、结构版本核对、接口/任务核验命令与预期成功标志。
6. **回滚方案与不可逆边界**：应用代码与配置回滚步骤、数据库回滚方式；凡涉及删表/删列、不可逆洗数或不支持反向 DDL 的结构升级，必须显式标注“不可直接回滚”并给出应急恢复路径（如停写、保留并核对升级后新数据、从升级前已验备份恢复并切回匹配版本程序）。
7. **变更来源追踪**：涵盖的提交范围/主要 PR 列表，以及已知风险或遗留限制。

#### 5.3.4 配套部署脚本底线与本地校验
- **单套参数化脚本覆盖测试与生产**：环境差异通过命令行参数、环境变量或外部配置文件注入，严禁在脚本内硬编码环境地址、账号或明文密钥。
- **防呆与严格失败**：Shell 脚本使用 `set -euo pipefail`（其他语言采用等价严格错误处理）；入口校验必需参数、环境变量与前置依赖命令，缺失立即非零退出并报错；写操作或高风险动作支持 `--dry-run` 或明确确认门禁。
- **本地静态校验（提交前强制）**：
  - Shell 脚本执行 `bash -n`（若本机已有 `shellcheck` 可附加检查，不因缺失而新增依赖或安装软件）；
  - Python/Node 等脚本执行对应原生语法检查（如 `python3 -m py_compile`、`node --check`）；
  - 若脚本支持无副作用的 `--help` / `--dry-run` 检查，可在本地隔离环境做干跑校验；
  - 严禁在发版阶段连接测试或生产主机执行任何命令。

#### 5.3.5 数据库 SQL 用途前置分类、双轨规则与五条硬阻断门禁

在执行排序或归拢前，必须先完成两步前置识别：

1. **按实际机制识别受管迁移**：不只按第三方框架名称（Flyway、Liquibase、Alembic、Prisma、Django Migrations、golang-migrate）匹配，还须识别**项目自建的顺序迁移机制**——凡存在版本化顺序迁移目录 + 数据库版本历史/校验和/目录摘要核对 + 专用迁移入口命令的，均归入受管迁移（轨道 1）。
2. **先按项目实际入口给全部区间 `.sql` 分类**：依据项目部署手册、脚本入口、目录命名与文件内容，将版本区间内触及的每一个 `.sql` 先划入四类之一，再决定去向：
   - **空库初始化（Bootstrap / Init）**（如 `dbinit.sql`、全量建表基线脚本）：仅归入“新装/空库初始化”说明，**绝不混入存量升级清单或存量升级脚本**；
   - **存量增量升级（Upgrade）**：纳入本次存量升级清单与执行顺序；
   - **回滚 / 恢复脚本（Rollback / Recovery）**：仅归入回滚章节，绝不放入正向升级顺序；
   - **测试 / 夹具 / 示例脚本（Test / Fixture / Seed-demo）**：明确排除出生产/测试运维执行清单。

完成分类后，按双轨规则处理：

- **轨道 1 — 项目使用受管迁移机制（含第三方框架与自有迁移链）**：
  - **禁止**重写、合并、重命名或删除任何既有或新增迁移文件；
  - 盘点 `vPrev..HEAD` 新增迁移文件，核对版本号顺序、依赖链完整性及目标结构版本，扫描锁表、删列、非空无默认值、长事务回填等高风险语句；
  - 在 `DEPLOY.md` 列出完整迁移清单、适用起始结构版本、目标结构版本与标准迁移入口命令（含前置只读预检要求），在部署脚本中调用项目标准迁移命令；
  - **框架外零散 SQL 分流处理（支持合法混用、阻断误绕过）**：
    - 检出位于受管迁移目录之外且划为存量增量用途的 `.sql` 文件时，区分其性质：若为常规表结构 DDL（疑似开发者误绕过迁移机制），触发下方第 4 条硬阻断；若明确属于迁移机制无法承载的合法运维/DBA 手工步骤（如建扩展、账号赋权、非事务在线操作、迁移后分批洗数），保留原迁移文件不变，若项目已有归档规范则直接引用原路径与顺序，无规范时将该手工 SQL 收入本版本 `sql/` 目录，并在 `DEPLOY.md` 显式标明相对标准迁移命令的执行顺序（`pre-migration` / `post-migration`）。
- **轨道 2 — 项目无受管迁移机制（手工零散 SQL）**：
  - 仅针对划为**存量增量升级**的 `.sql` 进行排序整理（空库初始化与回滚分别归入对应章节，不混入）；
  - 若项目已有 SQL 归档目录规范，在 `DEPLOY.md` 中列出原路径、来源 PR/提交与评审确认的执行顺序，不重复拷贝造成双份漂移；若项目无归档规范，则按执行依赖（前置检查 → DDL → 存量数据迁移 → 索引/约束/初始化配置）整理进本版本 `sql/` 目录并注明来源 PR/commit；
  - 尽量补齐前置检查或幂等保护（如 `IF NOT EXISTS`），并在 `DEPLOY.md` 标明适用起始基线，同时提示已在开发环境逐 PR 执行过部分语句时的差异注意。
- **五条硬阻断条件（命中任一项立即在只读预检阶段暂停，停在本地不写入脏文件、不推进 `main`、不打 tag，交由人工确认）**：
  1. 多个 PR 修改同一张表/同一字段存在语义冲突或顺序歧义，无法确定面向 `vPrev -> vNext` 的净 SQL；
  2. 存在删表、删列、改列类型可能导致数据截断、大表锁表风险，或依赖线上存量数据的不可逆洗数 DML，且未见明确人工确认或分步发布方案；
  3. 代码 diff 中明显存在实体/表结构/查询字段变更，但版本区间内找不到对应的数据库迁移文件或 SQL（疑似漏提库表变更）；
  4. 受管迁移项目中，出现**已判定用于存量升级**、位于受管迁移链之外且疑似绕过该机制的常规表结构 DDL，须人工决定改写为正式迁移文件或明确批准作为框架外步骤（已明确判定仅供空库初始化的脚本不命中本条；用途无法判定时走第 5 条）；
  5. 版本区间内存在无法从项目入口、手册或内容明确判定用途（空库初始化 / 存量升级 / 回滚 / 测试）的 `.sql` 文件，须人工确认用途后再继续。

### 5.4 Ezone 平台能力对齐与 `Provider Result` 统一定义

对照本仓库 `skills/ezone/scripts/ezone_release.py`（`POST /tags` 一次创建代码标签与 `releaseNote`；`PUT /tags/{name}` 修改说明尚未在真实平台验证对已有 annotated tag 的影响），`finishing-a-development-release` 的 Ezone 契约与四级状态统一定义如下：

#### Ezone 写入与回读契约
- **正常 Ezone 全量发版**（已授权 tag + 平台 Release，且 `ezone` Skill/CLI 身份与目标仓库预检可用）：
  1. 先推送 `main`（或合入受保护分支发布 PR 并锁定平台返回的实际合并 SHA）并回读精确 `main_sha`；
  2. **跳过**本地 `git push <tag>`，直接调用 `ezone` 创建代码标签与版本说明（传入精确 `--commit <main_sha>`、`--message <短摘要>`、`--body-file <notes>`，默认 `--no-notify`，仅用户明确授权通知并指定对象时使用 `--at`）[通知默认为 Agent 默认决定]；
  3. 执行**双回读**：通过 `ezone` 回读标签说明（核对固定合并 SHA、正文与 `atMembers`），并通过 `git ls-remote` 回读远端 tag ref（确认 tag 存在且指向或 peeled 指向精确 `main_sha`，记录平台返回的标签对象形态）；
  4. 错误分级：若 `ezone` 创建失败且回读确认远端无该 tag，结果为 **`Blocked`**（不误报为 `Partial Release`）；若远端 tag 已创建但说明内容或回读校验失败，结果为 **`Partial Release`**。
- **仅授权 Git tag 未授权平台 Release，或预检 `ezone` 不可用**：
  - 退回纯 Git 路径（`git tag -a` + `git push <tag>` + `git ls-remote` 回读），按下方统一的 **`Portable Release`** 收口（预检判定可用且已授权但实际写入/回读失败，必须报 `Partial Release` 或 `Blocked`，绝不临时降级为 `Portable Release`）。
- **Ezone 历史 tag 补建平台 Release**：
  - 在 `ez release edit`（`PUT /tags/{name}`）于隔离测试标签上实测确认不改写已有 annotated tag 对象与 peeled target 之前，对 Ezone 历史 tag 补建明确标为**未验证并阻断（`Blocked`）**，禁止盲目调用。
- **原则边界**：不在 `finishing-a-development-release/SKILL.md` 中复制 `ezone` 的 CLI 命令参数或认证实现，仅声明调用条件、消费回读结果与状态映射。

#### 统一后的四级 `Provider Result` 定义（消除“未授权”与“能力不可用”冲突）
保留现有四种结果名称不变，仅明确细化 `Portable Release` 的两种合法原因，使 GitHub、Gitee、Ezone 与未知平台遵循同一套状态与清理规则：

| Result | 可观察谓词 | 最终报告 `Platform release` 标示 |
| --- | --- | --- |
| `Full Release` | 目标 `main`（含发布 PR 实际合并 SHA）、远端 tag、原生平台 Release 与各自回读全部完成。 | `<release URL / verified id>` |
| `Portable Release` | `main`、annotated tag、版本化 `CHANGELOG` 与 Git 回读全部完成，且平台 Release 属于以下两种合法不执行原因之一：（1）**平台无可用 Release 能力**；（2）**本次仅授权 Git 发布、未授权创建平台 Release**。 | `unavailable` 或 `skipped (not authorized)` |
| `Partial Release` | 预检确认平台 Release 可用且已授权，`main`/远端 tag 已发布，但平台 Release 创建或回读校验失败。 | `failed (<reason & retry source>)` |
| `Blocked` | `main`/tag 写入失败、版本/基线/notes/remote 无法确定、部署材料或 SQL 硬阻断、发布 PR 待审未合入，或 Ezone 历史 tag 补建未验证阻断。 | `not run (<blocker>)` |

### 5.5 `review-and-release-pr` 的最小衔接

在不改变 `skills/review-and-release-pr/` 顶层目录布局与 frontmatter 路由边界的前提下，仅对其 `SKILL.md` 做两处精准更新：

1. **Phase 0 授权记录**：明确区分“单 PR 合并（merge）”、“正式切版本发版（tag/Release）”、“部署材料准备（deployment package）”以及“创建/合入独立发布准备 PR”；单 PR 合并授权不自动放大为切正式版本或生成整版部署材料，一次明确涵盖切版本发版的请求则沿用授权并跨阶段透传。
2. **Final verification and release handoff**：
   - 日常合入单 PR（不切版本）不触发跨版本部署材料整理；
   - 进入正式切版本发版 handoff 给 `finishing-a-development-release` 时：受保护分支遵循“先合入已 `PASS` 的功能 PR 并传递平台返回的实际合并 SHA，再由发布流程基于该基线建独立发布准备 PR 承载部署材料并遵守任意路径可执行部署内容的独立审查门禁”，不把跨版本产物塞回已审过的原功能 PR；
   - 透传已知版本号/显式起点基线线索、PR 范围与过程产物线索、以及用户对部署材料的显式开启/跳过指令；不在 `review-and-release-pr` 中维护第二套部署或 SQL 规则。

### 5.6 授权边界、Cleanup Gate 适配与最终报告合同

- **按动作独立核对的授权补充**：
  - 用户明确授权切版本发版即涵盖在隔离准备分支/待发布分支中新增并提交该版本部署材料；
  - **独立发布 PR 授权**：在受保护分支需要创建或合入独立发布准备 PR（如 `release/<version>`）时，按动作核对 PR 创建与合并授权，且包含新增/修改可执行部署内容的发布 PR 不得跳过独立审查或人工审批门禁；
  - **始终需要单独确认或硬停的事项**：覆盖或改动已存在的同版本部署目录（内容完全一致时直接复用）、删除仓库内原有零散 PR 过程产物、解决五类 SQL 硬阻断、缺少关键部署事实或无法唯一判定 `vPrev`、发布 PR 合并树因并发前移发生实质变化、Ezone 历史 tag 未验证补写，以及任何向测试/生产环境的远程执行（本 Skill 永不执行远程部署）。
- **Cleanup Gate 必要适配（保持六项门禁不变，补齐新路径的等价判据）**：
  - 第 3 条（`main` 已更新并回读）：既涵盖直接 `push main` 并回读，也涵盖受保护分支经发布 PR 合入后锁定平台返回的**该发布 PR 实际合并 SHA** 并核对合并树与最终验证树一致；
  - 第 4 条（tag 已发布并回读）：GitHub/Gitee/Portable 沿用 `annotated tag` 推送并回读；Ezone 经 `ezone` 一次创建的全量发版，以 `ezone` 回读与 `git ls-remote` 双回读确认 tag 锚定精确实际合并 `main_sha` 为等价满足条件；
  - 第 5 条（provider 结果）：`Full Release` 或 `Portable Release`（无论原因是平台无能力还是未授权平台 Release，只要满足各自回读谓词）均可进入已授权清理；`Partial Release`、发布 PR 待审等待态（`Blocked: release PR awaiting review/merge`）与任何部署/SQL 硬阻断均不进入 cleanup。
- **最终报告合同**：在 `finishing-a-development-release` 现有紧凑报告模板中新增 `Deployment package` 字段：
  ```text
  Release / Version/tag / Main / Tag / Platform release / Deployment package / Verification / History / Local state / Cleanup / Residual risk
  ```
  其中 `Deployment package` 清晰报告四种状态之一：`skipped (<reason>)`、`reused (<path>, baseline <vPrev>)`、`generated (<path>, baseline <vPrev>, checks <results>, pr-artifact notes)` 或 `blocked (<reason>)`。

### 6.2 验收基准与首批真实回放场景

除自动化布局/路由/链接单元测试、`quick_validate.py` 与 `git diff --check` 外，行为验收应覆盖以下三类源于真实业务仓库边界的脱敏场景与离线回放（不把私有仓库凭据、内网地址或业务敏感数据写入公开仓库）：

1. **空库初始化 + 多增量 SQL 共存（首选验收场景）**：模拟同一版本区间同时修改 1 个空库初始化脚本（如 `dbinit.sql`）与多个独立 SQL 文件且项目已有 SQL 归档规范的场景，验收运维仅凭输出文档即可明确判断：已有存量库应执行哪几个文件、顺序如何、哪些文件仅限空库新装禁止在存量库执行。
2. **项目自有顺序迁移链 + 生产跨版起点 + “每版必出”仓规深浅分流**：模拟非第三方框架的自建迁移链（带版本历史/校验和核对）、连续发布后生产跳过某版本尚未部署的起点核对提示（含显式指定起点），以及同一“每版必出”仓规仓库下的两种版本——无运维变更版本产出简短升级说明、含迁移与配置变更版本交付完整部署步骤；另在受管迁移仓库中分别验证“空库初始化建表脚本（正常分类不误阻断）”与“框架外存量升级建表脚本（命中第 4 条硬阻断）”。
3. **打 tag 后生成不可变制品摘要的边界**：模拟容器镜像 `sha256` 摘要须在打 tag 触发构建后才产出的仓库，验收标签内 `DEPLOY.md` 写明制品拉取核验方式与发布后最终摘要查询来源、不臆造摘要。
4. **安全与流程核心回归场景**：首次发版完整文件树盘点、本地 `main` 遇 SQL 阻断后提交指针与主工作区（含用户原有改动）均保持干净、保护分支独立发布 PR 锁定实际合并 SHA 与自定义目录可执行脚本独立审查门禁、Ezone 一次创建 tag+Release 双回读、平台有能力但未授权平台 Release 报 `Portable Release (skipped: not authorized)`，以及纯工具仓库快速路径跳过部署材料。

### 6.4 本设计中的 Agent 默认决定清单（已同步修订）

1. **常规快速路径零回归 + 本地 `main` 提交与工作区双保护**：未命中部署材料时完全保留原有顺序；命中部署材料的本地合并路径（包括起点就在 `main` 且需写材料时）一律先过只读预检并在独立准备分支/worktree 隔离生成与校验，通过后再集成 `main`，阻断时一律保留准备区且沿用既有 Cleanup Gate，确保本地 `main` 提交指针与主工作区（含用户原有未提交改动）保持原貌。
2. **显式跳过覆盖仓规 + “每版必出”仓规按实际变更定深浅**：按仓库 `AGENTS.md`，用户明确跳过时直接放行并在报告记录覆盖理由；未跳过且目标仓库规则明确要求每版提供部署记录时必须触发，但仍盘点实际变更——有运维动作出完整步骤与脚本，确认无运维动作才出简短记录。
3. **版本基线锚定与首次全量盘点**：正式版本默认以“上一个稳定 tag”为编写基线，同时允许显式指定实际起点并在文档写清应用/数据库起点核对方法；首次发版无历史 tag 时直接盘点目标提交完整文件树（不用 `initial_commit..HEAD` diff）。
4. **安全保护与幂等复用**：历史 tag 补建平台 Release 不触发入库部署材料生成；同版本目录已存在时先比对，内容完全一致直接复用，仅在实际需要覆盖或修改时暂停确认。
5. **`ezone` 默认不通知 + `Portable Release` 定义统一**：调用 `ezone` 创建 Release 默认 `--no-notify`；统一保留四级状态，在 `Portable Release` 中明确区分“平台无可用 Release 能力”与“仅授权 Git 发布、未授权平台 Release”。
6. **首版不预写跨栈自动采集脚本**：先通过渐进加载规则与真实版本回放验证，确认高频重复机械步骤后再决定是否提取脚本。

# 代码变更审查：改动导读、PR 适配、新概念质疑与零信任立场

## 目标

让不熟悉本次改动的人先看懂它在做什么：解决什么业务问题、怎么实现、架构怎么处理、改动怎么分组、引入了哪些新概念，以及作为一个 PR 是否合适。之后的审查流程（九个审查面、P0/P1/P2/C/Q、合并结论）保持不变，并将对抗性零信任姿态前置到全流程。

触发原因：现有报告从结论和问题开始，读者要先读懂代码才能理解结论；历史 PR #258 的回放中，“这个 PR 原样组织不合理”的判断出现偏晚；后续对大型跨端 PR 的复盘还暴露出把 PR 自带 PRD 当作已批准范围、未主动质疑新概念以及大 PR 报告跨节复述的问题。

## 非目标

- 不做“只导读、不审查”模式。
- 不新增参考文件，不改变已有锚点和下游 `review-and-release-pr` 的行为。
- 不同步其他仓库内的 Skill 副本。

## 报告顺序

1. 一行结论：合并结论与阻塞项数量。
2. 改动导读：详细、易懂的纯事实拆解（末尾给一行 PR 适配结论，不提前展开缺陷与处置方案）。
3. 特别提醒与完整判定：沿用现有规则；特别提醒压缩为单行清单。
4. 五问：只写判断（每问 2–3 句），引用导读和编号，不重复叙述。
5. 具体问题、验证与覆盖范围。

## 改动导读

| 部分 | 内容 | 规则 |
| --- | --- | --- |
| 业务问题 | 要解决什么 | 标明来源：PR 描述或 issue 写的标“声称”并与代码核对；从代码推断的标“推断”；查不到写“未说明”，不编造。缺口影响结论时才升级为 Q |
| 实现方式 | 主路径 3–5 步 | 入口 → 处理 → 存储或输出 |
| 架构处理 | 职责、依赖方向、数据归属的前后对比 | 无变化写“无架构变化” |
| 改动分组 | 按目的分组，给文件数和手写行数 | 业务功能、支撑性重构、机械改动、测试、文档、依赖配置 |
| 新概念清单 | 覆盖变动涉及的全部类别及来源（已确认 / 仅作者） | 数据/状态、机制、角色/权限、流程/入口、界面用词、共享依赖；只列事实，质疑与简化方案写在后文“方案” |
| PR 适配 | 合适 / 建议拆分（不阻塞）/ 违反仓库强制规则（C） | 见下节 |

单一分组的小改动只写三行。

图示只在文字讲不清时使用：主路径跨 3 个以上模块或进程、架构变化、异步或重试、状态流转、部署顺序依赖。只画已核实的事实，未追到的调用画虚线并标“未核实”；标出新增、修改、删除的节点；单图不超过约 12 个节点，常规审查最多 2 张；文字仍能独立读懂。发布到无法确认能渲染 Mermaid 的平台时，改用缩进文字和箭头。

## PR 适配判断

采用通用结构判据：PR 边界取决于这个单元能否独立说明、验证、决定合并或撤回，以及评审者能否看清关键差异，不取决于作者耗时或体量。规划阶段的风险面清单、固定行数阈值、分支时长提醒和具体仓库专有术语不写入 Skill；目标仓库有这类规则时在审查时读取，并以仓库规则为准。

对每个改动分组问三个问题：

1. 能否单独交付：单独合入后系统能运行，评审者能单独验证，撤回不影响其他功能。
2. 值不值得拆：拆开后关键差异更容易审清，或回滚范围更小。
3. 拆开是否有害：会产生无法验证或不安全的中间状态。

前两问为“是”且第三问为“否”时才建议拆分。耗时、经过时间、体量小或体量本身都不是理由。手写核心行数只说明评审负荷，仓库阈值只用来提示寻找上述边界。违反仓库强制拆分规则按 C 处理；其余拆分建议不阻塞合并。

## 新概念盘点与质疑（2026-11-27 补充）

触发：对一份 55 文件、跨前后端和共享权限服务的真实业务 PR 复盘显示，旧版首轮把 PR 自带的新增 PRD 当成已批准需求，判为“符合”且“建模克制”；追问后才发现权限收紧与既有协作决策冲突、界面出现作者自拟用词、用手工补录按钮代替真实操作驱动状态、并发锁机制用到了不需要的动作、为单模块需求修改共享服务。

这些问题都是 PR 新引入的概念。导读增加“新概念清单”，覆盖变动涉及的数据/状态、机制、角色/权限、流程/入口、界面用词和共享依赖；在“是否需要一起交付”中要求按涉及类别和具体动作追问三件事：从哪来（已确认来源或仅作者）、去掉后哪项用户任务做不成、有没有更简单的做法。PR 自带的新增或改写文档只算作者声称。与已确认来源冲突记 C；没有已确认来源时从用户任务和现有行为推断并标明是评审判断，有更简单做法时在方案回答中建议简化或移除，默认不阻塞。

不采用“强制依赖产品原型/PRD 对照”的写法：很多仓库没有这些文档，而且漏判的根源是没有主动质疑，不是缺少对照文档。有已确认来源时作为更强的依据使用。

## 零信任立场与报告去重（2026-11-27 补充）

触发：第二轮大 PR 盲测暴露两个问题——完整报告达 29,503 字符（导读新概念表、特别关注、五问与九面反复展开同一批事实和建议），且审查开头仍隐含“默认大方向合理、再挑违规”的合规姿态，报告中出现无证据的礼貌性肯定。

调整：
1. 在入口前置 `## Stance`，明确“零信任调查 + 证据门槛定级”：需求、PR 描述、自带文档、方案抽象、测试绿灯和既往主张一律先视为未证实假设，默认新增概念不必要直至用户任务证明必要，禁止无证据的客套肯定；同时维持严格的阻塞门槛（仅可证实的可达影响、基线冲突或关键前置缺口可阻塞），未证实的需求/方案质疑直接写透并标明为非阻塞评审判断。
2. 保持改动导读详细、完整、易懂（只写事实，新概念清单仅列类别/概念/来源），消除后文复述：一条事实或问题只展开一次，别处按节名或 `C/P/Q` 编号引用；特别关注改为单行清单；五问压缩为每问 2–3 句纯判断（新概念质疑与保留/简化/拆分/移除集中写在“方案”一次说透）；九面中已改动面只标“无异常”或对应问题编号，仅对未验证面展开缺口。

## 落地位置与体积

- `SKILL.md`：前置 `## Stance`；新增 `## Brief the change`；在 `## Does the whole change need to go together?` 加入新概念质疑与 `PR fit`；调整 `## Report and verdict` 顺序与去重约束。首版设计预期入口约 11 KB，两轮补充后实际为 13,685 字节（常规分支审查总读取量 27,171 字节，较按需加载重构前的 44,947 字节仍减少 39.5%）。
- `references/output-template.md`：加入导读模板、图示规则与后文精简去重约束（4,731 字节）。
- `references/pr-comments.md`：在评论模板顶部同步结论行与导读行（含新增概念与文字箭头降级，5,788 字节）。
